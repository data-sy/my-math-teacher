0% 유실은 공짜가 아니었다 — 1-vCPU 함정

전송 레이어는 요청을 한 건도 떨어뜨리지 않았다(전 런 502=0). 하지만 단일 vCPU에서는 캡 없는 컷오버에 숨은 실패모드가 있다 — 부팅 중인 JVM이 서빙 중인 JVM을 굶겨 요청이 타임아웃된다. 부팅 컨테이너의 CPU를 캡하면 사라진다.

컷오버 중 요청 유실 — 세 가지 구성

(502 + 전송 타임아웃) / 전체 · 축 0–15%
해석: 무제한 CPU는 한 번은 운으로 통과했지만(R1, 컷오버가 부하창 끝에 살짝 걸침) 넉넉한 마진 재측정(R2)에서 11.4% 타임아웃을 드러냈다. --cpus=0.5 캡(R3)이 이를 제거 — 같은 메커니즘, 굶김 없음.

근본원인 — 1 vCPU 위 부팅 컨테이너 CPU

컷오버 순간 docker stats · 축 0–160% · 점선 = 100%(1코어)
해석: 캡 없는 JVM 부팅(JIT + 클래스로딩 + Spring 컨텍스트)이 박스의 148%를 잡아 서빙 JVM을 굶긴다. 반코어 캡이 이를 55%로 눌러 서빙 컨테이너에 여유를 남긴다. 메모리는 한 번도 한계가 아니었다 — 2-JVM 공존 피크가 350 MiB 예산 중 ~247 MiB.
이번 런 · 라이브 재검증

두 안전장치를 end-to-end로 실행

둘 다 이전 작업에서 코드완료 상태였고, 이번 런에서 실제 배포 파이프라인 — apply·시드·SSM 배포·의도적 결함주입 — 에 대고 증명했다.

① CPU 캡을 파이프라인에 배선
배포 워크플로가 이제 CPU_LIMIT=0.5를 SSM을 거쳐 컨테이너 run까지 넘긴다 — 안 쓰이던 노브가 아니라 실제로.
✓워크플로 → docker run --cpus=0.5: green이 NanoCpus=500000000(½코어)으로 기동.
✓캡 하의 컷오버: 502=0 · transport_err=0, threshold PASS, p95 312 ms.
✓갭 발견: --ref 디스패치는 원격 워크플로를 돌린다 — push 먼저 안 하면 캡이 조용히 무반영.
② smoke 게이트가 데이터경로까지 검사
컷오버가 더는 의존성 없는 /health를 믿지 않는다 — flip 전에 실제 데이터 엔드포인트의 non-empty 형태를 폴링한다.
✓정상 경로: /concepts/nodes/7925 non-empty 반환 → 컷오버 진행.
✓결함 주입(엔드포인트 → 401): smoke RED → 컷오버 abort, 구버전 유지, exit 1.
✓abort는 완전 no-op: nginx는 여전히 green 서빙, 신규 컨테이너 폐기.

정직하게

이 리포트가 주장하지 않는 것

  • 2,000회 중 27회는 부하 생성기가 못 보낸 것이지 서버가 떨어뜨린 게 아니다. CPU 캡 부팅 스파이크(max 7.4 s) 동안 k6의 VU가 포화돼 아예 발사되지 않았다 — 클라이언트측 천장이지 서빙된 요청의 실패가 아니다. 발사된 요청은 전부 200.
  • 0% 유실은 부팅 CPU 캡을 전제로 한다(t3.micro의 단일 vCPU). 대안 — 2-vCPU 인스턴스 — 은 캡 없이 경합을 없앤다. 비용 vs 배포속도 트레이드오프.
  • 캡은 부팅을 ~2배 느리게 한다(헬스 12/30 ≈ 60 s vs. ~25 s). 백그라운드 컷오버엔 수용 가능 — 숨기지 않고 명시.
  • 0.5는 1회 측정값이다. 0.6 / 0.75가 부팅속도 vs 서빙보호 곡선에서 더 나을 수 있어 튜닝 후속으로 남긴다.
