Milestone 4 · Blue-Green Deployment

Making a single-EC2 deploy survive live traffic

A portfolio backend was redeployed by restarting its one container in place — 60.3% of requests failed during every deploy. This is the measured result of rebuilding that around an nginx blue-green cutover, and the honest boundary of where it reaches true zero loss.

The nuance

Zero loss wasn't free — a 1-vCPU trap

The transport layer never dropped a request (502 = 0 in every run). But on a single vCPU, an unthrottled cutover has a hidden failure mode: the booting JVM starves the serving one, and requests time out. Capping the boot container's CPU removes it.

Request loss during cutover — three configurations

measured as (502 + transport-timeout) / total · axis 0–15%
Read: unlimited CPU passed once by luck (R1, cutover grazed the load window's edge) then exposed an 11.4% timeout under a full-margin retry (R2). The --cpus=0.5 cap (R3) removes it — same mechanism, no starvation.

Root cause — boot container CPU on 1 vCPU

docker stats at the cutover instant · axis 0–160% · dashed line = 100% (one core)
Read: an unthrottled JVM boot (JIT + classload + Spring context) grabs 148% of the box and starves the live JVM. The half-core cap holds it to 55%, leaving the serving container headroom. Memory was never the limit — 2-JVM peak sat at ~247 MiB of the 350 MiB budget.
This run · live re-verification

The two safeguards, exercised end-to-end

Both were code-complete from prior work; this run proved them against a real deploy pipeline — apply, seed, deploy over SSM, and a deliberate fault injection.

① CPU cap wired into the pipeline
The deploy workflow now passes CPU_LIMIT=0.5 through SSM into the container run — not just an unused knob.
✓Workflow → docker run --cpus=0.5: green booted at NanoCpus=500000000 (½ core).
✓Cutover under the cap: 502=0 · transport_err=0, threshold PASS, p95 312 ms.
✓Caught a gap: --ref dispatch runs the remote workflow — push first, or the cap silently no-ops.
② Smoke gate covers the data path
The cutover no longer trusts a dependency-free /health — it polls a real data endpoint for a non-empty shape before flipping.
✓Green path: /concepts/nodes/7925 returned non-empty → cutover proceeded.
✓Fault injected (endpoint → 401): smoke went RED → cutover aborted, old version kept, exit 1.
✓Abort was a true no-op: nginx still served green, new container discarded.

Kept honest

What this does not claim

  • 27 of 2,000 iterations were dropped by the load generator, not the server. During the CPU-capped boot spike (max 7.4 s), k6's VUs saturated and never sent them — a client-side ceiling, not a served-request failure. Every request that was sent got 200.
  • Zero loss is conditional on the boot CPU cap on t3.micro's single vCPU. The alternative — a 2-vCPU instance — removes the contention without a cap, trading cost for deploy speed.
  • The cap slows boot ~2× (health at 12/30 ≈ 60 s vs. ~25 s). Acceptable for a background cutover; noted, not hidden.
  • 0.5 is one measured point. 0.6 / 0.75 may sit better on the boot-speed vs. serving-protection curve — left as a tuning follow-up.
