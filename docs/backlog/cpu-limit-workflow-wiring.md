# [M4 후속] 배포 워크플로에 CPU_LIMIT=0.5 기본 배선

## 배경

§4 무중단 측정(2026-07-05)에서 t3.micro(1 vCPU) blue-green 컷오버 중 신규 컨테이너의
JVM 부팅이 단일 코어를 독점(관측 148% CPU)해 서빙 중인 구버전을 굶기는 현상을 확인했다.
nginx 원자적 전환과 502 는 무결(전송갭 0)이나, 서빙 JVM 지연이 클라 타임아웃(10s)까지
밀려 지속부하 시 최대 11.4% 요청이 타임아웃했다(순수 CPU 경합, 전송 실패 아님).

`switch-backend.sh` 에 옵트인 `CPU_LIMIT` 노브를 추가하고(커밋 `12f6931`), `CPU_LIMIT=0.5`
재측정으로 `transport_err 133→0`·`p95 9984ms→3108ms`·유실 0% 를 확증했다.
트레이드오프: 부팅 ~2배 느림(헬스 12/30=60s vs 6/30=30s).

## 남은 작업

- [ ] 배포 워크플로 `api-ci-cd-with-ec2.yml` 의 deploy job 이 `runuser -l ec2-user -c '... bash
      deploy/switch-backend.sh <sha>'` 로 호출할 때 **`CPU_LIMIT=0.5` 를 env 로 전달**해
      실배포 경로에서도 완화책이 활성화되게 한다. (현재 노브는 있으나 워크플로가 안 넘겨줘 실배포는
      여전히 무제한)
- [ ] 값 튜닝 여지: 0.5 는 1 회 측정값. 부팅 속도 vs 서빙 보호 트레이드오프를 몇 점 더 떠서
      최적점 확인(예: 0.6/0.75). t3.micro burst 크레딧 상호작용도 고려.
- [ ] 대안 검토: 인스턴스를 2 vCPU(t3.small 등)로 올리면 CPU 캡 없이도 경합 소멸 —
      비용 vs 배포속도 트레이드오프. CPU_LIMIT 는 t3.micro 유지 시의 소프트웨어 완화책.

## 경계

- 이 배선은 재배포(라이브)로만 재검증 가능 → 다음 apply 세션에서 함께.
- 노브 자체(디폴트 무제한, 옵트인)는 이미 커밋됨 → 기존 동작 완전 보존, 되돌림 안전.
