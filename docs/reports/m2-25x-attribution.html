25배는 어디서 왔나

M2 리포트는 그래프 탐색 p95 14.034 ms → 0.556 ms 를 “작은 그래프에서는 MySQL 인덱스 JOIN 이 Neo4j native 탐색보다 빠르다”로 해석했다. 코드와 실행계획을 다시 재면, 그 배율의 대부분은 Neo4j 안에서 일어나지 않는다. 리액티브 리포지토리를 블로킹 스택에서 .block() 으로 소비하는 클라이언트 경로가 한쪽에만 얹혀 있었고, 비교 대상인 CTE 경로에는 그 비용이 없다.

Q1 · 호출 방식
리액티브 + block 이 맞다
ConceptRepository 는 ReactiveNeo4jRepository. 서블릿 스택(starter-web)에서 Flux 를 전부 .block() 으로 회수한다.
Q2 · 측정 지점
브리지 비용이 포함된다
baseline 표의 2·3·4·5행은 .collectList().block() 을 잰다. 1행(2.088 ms)만 드라이버 직접. CTE 쪽은 JdbcTemplate — 브리지 없음.
Q3 · 컨테이너 메모리
디폴트지만 교란요인 아님
스토어 792 KB < 페이지캐시 512 MB, PROFILE page cache 0/0. 각주는 필요하되 “왜곡 없음”을 못박는 형태여야 한다.

결론 · Q2

Neo4j p95 8~14 ms 안에 리액티브 브리지 비용이 포함된다. 그리고 비교 대상인 CTE 쪽 0.556 ms 에는 포함되지 않는다 — 비대칭은 한 방향으로만 작동한다.

코드베이스는 이 함정을 이미 한 번 문서화했다. QueryTimingAspect.java:22–23 — “Reactive 리포지토리는 @Around 가 Flux/Mono 조립 시간만 측정. 실제 Neo4j 쿼리 실행 시간은 측정되지 않음.” 관측 애스펙트에는 적용된 주의가 벤치마크에는 적용되지 않았다.

같은 파일이 스스로 반증하는 warmup 설정

여기에 두 번째 비대칭이 겹친다. baseline 표는 WARMUP_RUNS = 3, MEASURED_RUNS = 100 으로 산출됐다(GraphQueryPerformanceTest.java:60–61). 그런데 같은 파일의 회귀 테스트는 warmup 을 20으로 올려 놓았고, 그 이유를 명시한다:

GraphQueryPerformanceTest.java:239–241
// Task 2.2: 회귀 감지 테스트 — warmup 20 + 측정 30 회의 p50 (median) 이 ceiling 미만이어야 함.
// median 을 쓰는 이유: isolated 실행 시 cold JVM 의 첫 몇 회가 크게 튀어 avg 가 오염됨.
// warmup 20 은 Reactor + Neo4j driver 파이프라인 JIT 컴파일이 수렴할 때까지 필요.

그리고 baseline 문서 116행은 실제 관측을 기록해 뒀다 — “cold JVM 의 첫 수 회가 튀어 avg 가 오염 (depth3 avg=15ms, 베이스라인의 3배)”.

이것이 p95 에 무엇을 하는가

100회 측정을 정렬했을 때 p95 는 86–100번째 값이다. warmup 3회로 JIT 이 수렴하지 않았다면 느린 초기 반복들이 정렬 후 정확히 그 구간에 앉는다. 즉 p95 = 14.034 ms 는 “95%의 요청이 이 안에 들어온다”가 아니라 “JIT 미수렴 반복의 값”일 수 있다.

CTE 쪽도 warmup 3회지만(CteGraphQueryPerformanceTest.java:52) 데워야 할 코드 경로가 JdbcTemplate + HikariCP 로 훨씬 짧고, Spring 컨텍스트 기동 중 이미 상당 부분 데워져 있다. 같은 warmup 값이 두 경로에 같은 효과를 주지 않는다.

정황도 들어맞는다. 깊이 3 은 avg 5.392 대비 p95 14.034 로 tail 이 2.6배다. 결정론적 쿼리 작업이 만드는 모양이 아니라, 스케줄링 지터와 JIT 전이가 만드는 모양이다. 반면 CTE 쪽 p95 0.556 ms 에는 그런 tail 이 없다.

의견 · Q3 — 각주는 필요하다. 단, 지금 떠오르는 형태로는 안 된다.

“컨테이너 디폴트 메모리 설정”이라고만 적은 각주는 없는 의심을 만든다. 읽는 사람은 “튜닝을 안 해서 Neo4j 가 손해 봤나?”를 떠올리고, 그건 위 실측이 이미 기각한 가설이다. 792 KB 스토어가 512 MB 페이지캐시 안에 통째로 들어 있고 page cache 접근이 0회다.

각주는 사실 + 기각 두 절을 함께 담아야 한다. 예: “양쪽 컨테이너 모두 메모리 디폴트로 실행(Neo4j 페이지캐시 512 MB, MySQL 버퍼풀 128 MB). 스토어 792 KB 로 전량 상주하며 PROFILE 상 page cache 접근 0회 — 메모리 미튜닝은 본 비교의 교란요인이 아니다.” 사실만 적으면 재현성은 남지만 오독을 부르고, 기각만 적으면 근거가 사라진다.

후보별 기여 가능성

먼저 실행계획 실측 하나를 더 놓고 시작한다. 이게 직관과 가장 어긋나는 지점이다.

PROFILE · 깊이 3 · conceptId=6646 · 배포된 Cypher 그대로

실제 그래프 탐색은 44 DB hit. 나머지 3263 (98.7%) 은 앵커를 찾는 전수 스캔이다. 원인은 두 겹이다:

  1. concept.concept_id 에 인덱스가 없다 — init.cypher 에도, 벤치마크 시드에도 CREATE INDEX 가 없다. 확인된 인덱스는 시스템 LOOKUP 2개뿐.
  2. 인덱스를 만들어도 쓰이지 않는다. 패턴 (n {concept_id: $conceptId}) 에 라벨이 없어서 플래너가 라벨-속성 인덱스를 잡을 수 없다. 실제로 CREATE INDEX 후 재프로파일해도 DB hits 는 3307 그대로였다. (n:concept {…}) 로 라벨을 붙이면 NodeIndexSeek 2 hits 로 떨어지고 총합이 3307 → 46 이 된다.

그런데 이 72배의 DB 작업 감소가 벽시계로는 약 0.3 ms 밖에 안 된다(위 §2 표: 1.337 → 1.052 ms). 1631 노드는 전수 스캔해도 메모리 안에서 끝나기 때문이다. 이것이 이 분석의 핵심 반전이다 — 인덱스 부재는 사실이지만 25배의 원인이 아니다.

한 문장으로

25배 중 Neo4j 엔진 안에서 설명되는 몫은 약 10%이고, 그 10% 안에서도 절반 이상은 엔진이 아니라 쿼리 작성(라벨 누락 + UNWIND 증폭)이 만든 것이다. 나머지 90%는 한쪽 경로에만 얹힌 리액티브 클라이언트 스택과, 그 스택을 3회 warmup 으로 재서 p95 로 보고한 측정 설계가 만든 것이다.

M2 결정은 여전히 옳다

이 분석은 마이그레이션을 되돌릴 근거가 아니다. 운영 DB 1종 감축, 재귀 CTE 의 충분한 성능(깊이 5 p95 0.471 ms, 기준 100 ms), 결과 동치성 15/15 통과 — 모두 그대로다. 정정 대상은 결정이 아니라 서술이다. “Neo4j 가 이 워크로드에 느리다”가 아니라 “리액티브 리포지토리를 블로킹 스택에서 .block() 으로 쓰던 구조가 느렸고, 이관하면서 그 구조도 함께 걷어냈다” 가 실제로 일어난 일이다. 후자가 더 값진 교훈이기도 하다 — 다음에 또 저지를 수 있는 실수를 짚어 주기 때문이다.

이걸 확정할 실험 하나

위 귀속 추정에서 남는 불확실성은 실험 하나로 닫힌다. 프로덕션 코드는 건드리지 않는다.

  • GraphQueryPerformanceTest 에 벤치마크 1개 추가 — findNodesIdByConceptIdDepth3 와 동일한 Cypher 를 driver.session().run(…).list() 로 실행(이미 benchmarkFindById:137–142 가 쓰는 패턴 그대로).
  • 양쪽 다 WARMUP_RUNS = 20 으로 올려서 측정.
  • 두 값의 차이 = 리액티브 브리지 비용. warmup 3 대 20 의 차이 = JIT 기여분.
  • baseline 문서 표에 avg 와 p95 를 함께 싣고, 각 행에 측정 경로(드라이버 직접 / 리액티브)를 컬럼으로 명시.

이 분석의 한계. 서버측 실측은 2026-08-29 격리 컨테이너(neo4j:5.12, 동일 CSV, 노드 1631 / 관계 3446 재현 확인)에서 cypher-shell 로 300회 반복 후 RETURN 1 바닥값을 차감해 얻은 한계비용이다. JVM 드라이버가 아니고, 2026-04-24 baseline 과 Docker 상태도 다르며(측정 중 타 스택 구동), 같은 머신이지만 동일 조건 재현은 아니다. 따라서 “서버측 약 1.3 ms”는 자릿수 주장으로 읽어야 하고, 14.034 ms 의 3분할은 실측 1개 + baseline 문서의 avg·p95 로 구성한 귀속 추정이다. PROFILE 의 DB hits·행 수·플랜 연산자, 그리고 코드 인용은 모두 직접 확인한 사실이다. 프로브 컨테이너는 측정 후 제거했고 저장소 파일은 수정하지 않았다.
