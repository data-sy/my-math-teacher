# 🤖 [MMT] 프로덕션 재런치 / 티어다운 런북

> **새 세션(리포 접근 O)에 붙여넣어 실행하는 프롬프트다.** 프로덕션 인프라를 **고쳐진 상태로 재런치**하는 절차(§3)와, 다시 **완전 종료($0)** 할 때의 절차(§4)를 담는다.
> ⚠️ **비가역 작업**(RDS 삭제·EC2 terminate·EIP release)이다. **에이전트의 SSM `send-command`·프로덕션 HTTPS·AWS 뮤테이션은 분류기 차단** → 실제 실행은 **사용자가 맥에서**. 에이전트는 확인 명령·안전 순서를 **스크립트로 만들어 전달**만 한다(맥 오케스트레이터 스크립트 패턴).
>
> **📌 이 문서의 서술 규칙 (2026-08-07 정리):** 인스턴스 ID·IP·엔드포인트처럼 **재런치가 무효화하는 값은 적지 않는다** — 값 대신 **그 값을 얻는 명령**을 적는다. 라인 번호도 쓰지 않는다(`database.tf:24` 가 실제로는 32행이 돼 있었다). 여기 남은 고정값은 **재생성 불가능한 복구 앵커**(스냅샷 이름·커밋 해시·이미지 태그)뿐이다.

## 1. ⚠️ 실행 전 반드시 아는 3가지 (가정 교정)

1. **RDS 는 `skip_final_snapshot = true`** (`grep -n skip_final_snapshot infra/terraform/database.tf`) → 그냥 삭제하면 **DB 데이터가 스냅샷 없이 소멸**한다. concepts·지식그래프·유저 데이터가 여기 있다. **수동 스냅샷이 유일한 데이터 보존 수단.** (지금은 RDS 도 스냅샷도 없다 — 이 경고는 재런치 **이후** 다시 티어다운할 때를 위한 것이다.)
2. **인프라는 terraform 관리다 — 다만 state 를 먼저 본다.** 2026-08 재런치는 `apply` 로 세웠고 2026-09-08 은 `terraform destroy` 로 18개 리소스를 전부 내렸다(state 는 지금 비어 있다). spec-03·04 의 "plan-only 샌드박스 / 사람이 수동 프로비저닝" 은 그 이전 시절 서술이다. 그래도 `apply/destroy` 가 실제 리소스와 대칭이라 가정하지 말고 §2 에서 먼저 확인한다.
3. **호스트 상태는 terraform 밖이다.** env-file(시크릿)·certs·nginx `active-backend.conf`·Docker 이미지·DNS(도메인→EIP)·OAuth redirect-uri 등록은 IaC 로 복원되지 않는다 → §3-4 에서 손으로 복원.

## 2. 현재 상태 확인 (read-only · 값은 여기서 얻는다)

```bash
# 프로비저닝 방식 — 비었거나 라이브 리소스가 없으면 = 수동 프로비저닝(apply/destroy 무의미)
cd infra/terraform && terraform state list

# 실제 리소스 (ID·엔드포인트·EIP 를 여기서 확보)
aws ec2 describe-instances --filters Name=tag:Project,Values=mmt --profile mmt-admin
aws rds describe-db-instances --profile mmt-admin
aws ec2 describe-addresses --profile mmt-admin

# RDS 스냅샷 — 0개가 정상이다(2026-10-02 전부 삭제). 뭔가 보이면 그사이 누가 만든 것
aws rds describe-db-snapshots --profile mmt-admin

# DNS 현재 타깃
dig +short www.my-math-teacher.com
```

> **AWS 세션:** 프로파일 `mmt-admin`(assume-role + MFA, ~1h). MFA 는 대화형 터미널에서만 입력 가능하므로 사용자가 맥에서 `aws sts get-caller-identity --profile mmt-admin` 로 먼저 세션을 띄운다(`!` 실행·비대화형에선 에코 불가).
>
> ⚠️ **장기 휴면 후라면 두 가지가 막혀 있을 수 있다**(상세 = [ROADMAP](../../ROADMAP.md) 상단 "오래 비웠다 돌아왔다면"):
> ① `mmt-cli` 액세스 키가 **비활성화**돼 있다 → 콘솔 IAM 에서 Activate 해야 위 명령이 통한다.
> ② 도메인 등록 만료일이 **2027-06-17** 이다 → 그 뒤라면 도메인이 끊겼을 수 있으니 §3-2(DNS) 전에 `whois` 로 확인한다.

## 3. 재런치 런북 (고쳐진 상태로 복구)

1. **인프라 프로비저닝** — `terraform plan` → 전문에서 create/replace 개수를 읽고 → 승인 → `apply`(spec-02 G-gate). state 가 비어 있으므로 전부 create 여야 정상이다.
2. **DNS** — 새 EIP 로 `www` A레코드 생성(티어다운에서 삭제했으므로). **certbot 발급이 DNS 를 요구하니 호스트 복원보다 먼저** 하고, `dig +short www.my-math-teacher.com` 이 새 EIP 와 일치할 때까지 전파를 기다린다. OAuth 는 도메인 기반이라 DNS 만 맞으면 콘솔 재등록 불요.
   - ℹ️ 전파~서비스 기동 사이에는 **A레코드는 새 IP 를 가리키는데 80/443 은 아직 안 열린** 구간이 생긴다. 이 구간을 밖에서 보면 "죽은 IP 를 가리키는 dangling DNS" 처럼 보이지만 정상 진행 상태다(2026-08-05 재런치 중 실제로 그렇게 오독된 적 있음).
3. **RDS = 빈 인스턴스** — 1단계 `apply` 가 **빈 `mmt-db`(MySQL 8.4)** 를 만든다. 복원할 스냅샷은 없다(`database.tf` 에 `snapshot_identifier` 없음).
   프로덕션 유저·진단 기록은 2026-10-02 에 폐기됐으므로 되살릴 것도 없다.
4. **시드 적재** — ⚠️ **이 단계는 실증된 적이 없다**(이전 재런치는 전부 스냅샷 복원). RDS 는 `publicly_accessible=false` 라 **EC2 호스트 경유**로 넣는다.
   - 순서·옵션의 정본 = [`docs/DEVELOPMENT.md`](../DEVELOPMENT.md) "초기 데이터 적재"(FK 순서 · `--default-character-set=utf8mb4` 필수). 접속 대상만 로컬 컨테이너 → RDS 엔드포인트로 바꾼다.
   - `create.sql` 이 M7 자가진단 스키마와 M8 `concept_links` 테이블을 이미 품고 있다 → 별도 DDL 단계 없음(`m7-apply-…-prod.sql`·`m8-apply-…-prod.sql` 은 기존 DB 에 덧붙일 때만 쓴다).
   - 개념 링크 시드 = `bash shared/scripts/concept-links-seed-to-sql.sh > seed.sql` → 같은 경로로 적재(원본 `shared/data/concept-links-seed.csv`).
   - 호스트에 mysql 클라이언트가 없을 수 있다(minimal AMI) → `docs/handoff/scripts/host-readiness-check.sh --apply`.
   - 적재 후 행 수 대조: chapters 647 · concepts 1631 · knowledge_space 3446 (M4 재시드 실측, `docs/specs/m4/m4-worklog.md`).
   - 선행 권장: 로컬 컨테이너에서 같은 순서로 한 번 적재해 시드가 지금도 깨끗이 들어가는지 확인한다(`insert_concepts*` 변형 중 정본은 `insert_concepts_latex.sql`).
5. **호스트 복원** — `~/mmt-backend.env`(시크릿 재주입) · certbot 인증서 재발급(`web/nginx.conf` 의 webroot 챌린지 순서) · `active-backend.conf` · docker 네트워크 `mmt-net`. 프론트는 compose 아닌 `docker run` 직접.
   - ⚠️ **인증서 "재발급"과 "자동갱신 재등록"은 별개다 — 둘 다 해야 한다.** 2026-08-05 재런치가 재발급만 하고 갱신 경로를 안 옮겨, 만료(2026-11-03) 80일 전까지 **아무 증상 없이** 방치돼 있었다(2026-08-15 발견 → 08-19 해소). 옛 호스트의 systemd 타이머는 terminate 와 함께 소멸한다.
   - 재등록 = `docs/handoff/scripts/setup-tls-renewal.sh` (docker certbot + systemd 주간 타이머 + `nginx -s reload`). **dry-run 의 "all simulated renewals succeeded" 까지 봐야 끝난 것**으로 친다 — 타이머만 걸고 실증을 안 하면 "걸려 있다고 믿지만 안 도는" 상태가 된다(이번 사고의 형태).
   - 전제 확인: `/.well-known/acme-challenge/` 가 80 에서 **404** 로 응답해야 한다(301 이면 리다이렉트에 먹혀 갱신 실패).
6. **백엔드 재빌드·배포** — ⚠️ 마지막으로 배포됐던 이미지 `mmt2024/mmt-backend:889390a` 는 **인증 버그 수정(track A) 미포함이라 재사용 금지.** `feat/m7-item-selection`(≥ `1c7c29e`, 이상적으로는 머지된 main)에서 **재빌드한 새 태그**로 배포. 프론트는 `mmt2024/mmt-front:2.0.0` 재사용 또는 재빌드.
7. **플래그** — `MMT_DIAGNOSIS_ENABLED=true` (호스트 `~/mmt-backend.env`).
8. **검증(마스킹 해소 확증 — 수동)** — login 200 → `GET /learning-queues/me` 가 **404 또는 200**(401·500 이면 미해결) · 존재하지 않는 경로 → **404**(마스킹 제거 확인) · 무토큰 대조군 → 401.

## 4. 티어다운 절차 (다시 완전 종료할 때 — 재사용 틀)

> 2026-07-31 에 이 절차로 mothball 실행 완료. 리소스 ID 는 그때마다 §2 에서 새로 얻는다.
>
> **2026-09-08 사이클**은 스크립트 3개(`mothball-1-snapshot`·`mothball-2-destroy`·`mothball-3-residual`)로 돌렸다.
> 스냅샷 이름·EIP 가 하드코딩된 일회용이라 **2026-10-02 에 삭제했다** — 다음 티어다운은 아래 절차를 보고 그때 다시 만든다
> (참고가 필요하면 git 히스토리 `docs/handoff/scripts/mothball-*.sh`). 선행 = `bash ~/mmt-aws-session.sh <MFA 6자리>`.
>
> **2026-09-08 결정 (이전 사이클과 다른 점 — 재런치 때 반드시 읽을 것):**
> - **전체 destroy 를 택했다** (7개월 이상 휴면 전제). §4-8 의 "IAM/OIDC/keypair 는 $0 라 보존" 과
>   **다르다** — IAM role·OIDC provider·instance profile·keypair·SG 까지 전부 지웠다.
>   → **재런치 때 이것들을 다시 만들어야 한다.** terraform `apply` 가 코드에서 재생성하지만,
>   **GitHub Actions 쪽 배포는 OIDC provider·`ci_deploy` role ARN 이 새로 생길 때까지 실패한다** —
>   재런치 후 워크플로의 role ARN 이 실제 값과 맞는지 확인할 것(계정 ID 동일하면 ARN 도 동일).
>   SSH 개인키 `~/.ssh/mmt-ec2` 는 로컬 자산이라 살아남는다(공개키로 keypair 재등록).
> - **DNS 는 이 계정에서 못 지운다.** 도메인·호스팅 영역이 **타 AWS 계정**이다(spec-01 §67).
>   `mmt-session` 프로파일로는 Route53 접근 불가 → 그 계정 콘솔에서 `www` A레코드를 손으로 삭제한다.
> - **⚠️ Extended Support 지뢰.** 표준지원이 끝난 MySQL **8.0.x** 스냅샷을 복원하면 Extended Support 에 자동 편입된다
>   (8월 USD 149.41 사건 = [`docs/incidents/2026-08-rds-extended-support.md`](../incidents/2026-08-rds-extended-support.md)).
>   그래서 8.0 스냅샷 2개를 2026-09-08 에 지웠다. 엔진 버전은 `var.db_engine_version`(8.4) — 낮추지 말 것.
> - **2026-10-02: 마지막 스냅샷 `mmt-mothball-2026-09-08` 도 삭제**(사용자 결정 — 개발 데이터라 보존 불요, 과금·관리 대상 0 으로).
>   `database.tf` 의 `snapshot_identifier` 를 걷어냈고, 재런치 데이터 경로는 §3-3·§3-4 의 **빈 RDS + 시드 적재**다.

1. **RDS 최종 스냅샷 (필수 선행)** — `aws rds create-db-snapshot --db-instance-identifier <ID> --db-snapshot-identifier mmt-mothball-<YYYY-MM-DD>` → `aws rds wait db-snapshot-available ...` → `describe-db-snapshots` 로 **Status=available** 확인. **available 확인 전에는 다음 단계로 가지 않는다.**
2. **(해당 없음)** ~~스냅샷 직전 DDL 적용~~ — 시드 적재로 세운 DB 는 `create.sql` 이 스키마 전부를 품고 있어 따로 적용할 DDL 이 없다. 그 뒤 스키마를 바꿨다면 스냅샷 전에 적용해 둔다.
3. **재런치 상태 캡처(기록만, 시크릿은 리포 밖)** — 이미지 태그 · `~/mmt-backend.env` 키 목록(값은 안전보관) · `active-backend.conf` 내용 · certs 도메인 lineage · DNS A레코드 타깃 · OAuth redirect-uri 등록값.
4. **RDS 삭제** — `aws rds delete-db-instance --db-instance-identifier <ID> --skip-final-snapshot` (수동 스냅샷 확보했으므로 skip OK). 삭제 직전 스냅샷 available 재확인.
5. **EC2 terminate** — `aws ec2 terminate-instances --instance-ids <ID>`. EBS 루트가 delete-on-termination 기본이라 **certs 등 호스트 상태는 소멸**한다(재런치 시 재구성).
6. **EIP release** — `aws ec2 release-address --allocation-id <alloc>`. release 하면 IP 가 반환되어 재런치는 **새 IP** → DNS 갱신 필요. IP 유지가 중요하면 EIP 만 남길 수 있으나 미연결 EIP 는 소액 과금.
7. **DNS 정리** — 재런치를 곧 하지 않을 거면 `www` A레코드를 **삭제**한다. 반환된 IP 가 타 계정에 재할당되면 내 도메인으로 남의 서버가 서빙되는 **dangling DNS** 가 된다. 삭제 후 `dig` 로 실제 사라졌는지 확인할 것.
8. **잔여 정리** — 미사용 SG·EBS 스냅샷·CloudWatch 로그그룹 등을 `Project=mmt` 태그로 조회 후 판단. IAM/OIDC/keypair 는 $0 라 보존(재런치 마찰 최소화).
9. **검증은 exit code 말고 실제 state 로** — `describe-instances`·`describe-db-instances` 로 리소스 소멸 확인, 멱등 재조회. terraform state 를 썼다면 `state list` 빔 확인.
10. **휴면 중 남는 비용** — 수동 스냅샷 저장분뿐(~$0.095/GB-월). 인스턴스를 지워도 수동 스냅샷은 영구 보존된다. 반대로 **자동 백업(PITR)은 인스턴스와 함께 소멸**하므로, 수동 스냅샷이 available 인 것이 유일한 데이터 보존 증거다.
