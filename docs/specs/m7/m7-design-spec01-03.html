1. 무엇이 왜 바뀌었나 (피벗 서사)

문제 정의 — 문제 풀(problem pool)의 실부재

MMT 3기둥 = ① 지식그래프 시각화 · ② 진단 · ③ 맞춤학습지. 이 중 ②③이 공통으로 서빙 가능한 실문항에 의존하는데, 기존 items 8,120건은 가라 이미지 + 저작권 제약으로 공개 서비스에 올릴 수 없다. ①만 이 병목과 무관하다. 두 갈래(1. AI로 문제 생성 / 2. 우회) 중 품질 보장 불가로 1을 버리고 2를 택한 것이 M7 피벗이다 (밀스톤 §왜 피벗인가).

지식그래프를 테스트 엔진 자체로

MBTI식 "답에 따라 다음 화면이 갈리는" 흐름. "몰라요" → 그 개념의 선수지식으로 drill-down(무너진 토대의 바닥 찾기), "알아요" → 선수 폐쇄 전체를 inferred-known으로 skip. 개념 1,631개를 다 못 묻는 문제를 skip이 해소해 문답 수를 짧게 유지한다 (밀스톤 D2, spec-01 §4.3).

DKT 시급도 — "피벗의 피벗" (2026-07-13 개정)

2026-07-11 원안 D3은 "시급도 = 그래프 점수(blockedDescendants·depth 가중합), DKT 폐기"였다 — DKT에 self-report를 먹이면 garbage-in이라는 이유. 그러나 "가장 시급한 것부터 하나씩 배포" 전략상 진단 엔진 신규 구축을 보류하고 D3-R로 역전: 기존 DKT를 유지하되 self-report OX를 정오답으로 매핑해 입력. 트레이드오프(자기보고가 모델 출력을 왜곡하는 R1)는 감수하고, "AI 진단" 포지셔닝·자산을 보존하며 "인증"이 아니라 "자가진단 학습 가이드"로 정직 프레이밍해 방어한다. 이 개정으로 그래프 점수 전제의 구 spec-01 초안은 삭제(git 히스토리 보존)되고 현행 spec-01이 전면 대체했다 (밀스톤 D3·D3-R, spec-01 Supersedes).

밀스톤 결정 D1~D7 (2026-07-11 사인오프 + 07-13 개정)

  • D1 — 진단 = self-report OX. 문제 풀 부재 우회.
  • D2 — 진단 엔진 = 그래프 적응형 문답(개념 나열형 기각).
  • D3 → D3-R — 시급도 = 그래프 점수(폐기) → DKT 유지 + 정오답 매핑(위 카드).
  • D4 — 맞춤 = 그래프 학습 경로 + 외부 링크 큐레이션(07-13 확장 — 원안은 "링크만"). 학습지 출제 제거.
  • D5 — 문답 카드 = 개념 이름 + 대표 예시("내용은 아는데 이름을 몰라" 오답 방지).
  • D6 — React 새로 짜기 확정 + 범위 = 최소 런치 MVP 6화면(부가화면은 오픈 후 이식). 구 [Design] 트랙의 "React는 launch 후" 결론을 supersede.
  • D7 — 모바일 퍼스트. 레포는 모노레포 유지(새 레포 X — M2/M4/M6 서사 보존).

2. 3-spec 책임 분해

세 spec은 계약(spec-01) → 화면(spec-02) → 채움(spec-03)의 층위로 나뉜다. 순서 자체가 설계다: spec-01이 프론트가 소비할 전 계약(진입·문답·결과·큐)을 굳혀야 React 화면이 헛돌지 않고 (spec-01 §5), spec-02가 화면·hook 계약을 확정한 뒤라야 spec-03이 예약 지점을 채우는 층으로 역방향 의존 없이 얹힌다 (spec-03 §5).

spec-01 · 진단 백엔드 — 계약·데이터모델·큐 로직

(a) 확정한 것: 신규 API 네임스페이스 /api/v1/diagnosis/*(frontier·next·preview·귀속)·/learning-queues/* 전 계약, 서버 주도 stateless 적응형 순회(D1-A), self-report→DKT 매핑·저장(self_report_answers 신설 + probabilities.user_test_id additive), 결과 계약(헤드라인+카드 top-N+urgencyBasis+links:[] 예약), 통합 학습 큐(위상순 지배 정렬 + 재진입 2테이블), 결정 S1~S6.

(b) 왜 이렇게 나눴나: 백엔드 엔진과 API 계약에 한정 — 화면(spec-02)과 링크 데이터(spec-03)를 밖으로 밀어내 계약을 먼저 고정.

(c) 맞물림: spec-02의 8개 라우트가 이 계약을 소비하고, spec-03이 links:[]·큐 계약 위에 얹힌다. 구 진단 경로(/weakness-diagnosis·answers·findAIInput)는 무변경 보존 + 신규 경로 무접촉이 롤백의 전제.

spec-02 · 프론트 React MVP — 화면 6개·게이트 배선·상태관리

(a) 확정한 것: 스캐폴딩 스택 T1~T5(Vite+React19+TS / TanStack Query+Zustand / Tailwind+Radix / React Router v7 / web-react/ 병행), 크리티컬 패스 6화면 + /queue 라우트 맵, F-2 localStorage 계약(mmt.diagnosis.v1, append-only), F-1 게이트 배선(④ 2상태 + returnTo 복원), auth/API 레이어 재구현(현행 결함 2건 — 401 무대응·에러 상태 유실 — 을 승계하지 않고 개선), Cytoscape hook 포팅(호버 0 → 탭 바텀시트).

(b) 왜 이렇게 나눴나: spec-01 계약이 굳은 뒤라 화면-계약 매핑이 고정점 — React 작업이 백엔드 구현과 병렬 가능(mock으로 선개발). MVP 규모 산정 근거 = 현행 전역 상태가 accessToken 하나뿐이라는 실측.

(c) 맞물림: spec-01 shape를 TS 계약 타입 모듈(contracts.ts)로 옮겨 SSOT 유지. ④ 게이트 뒤 그래프·hook 확장 지점은 spec-03에 계약만 예약.

spec-03 · 맞춤 — 외부 링크 + 그래프 경로 노출층

(a) 확정한 것: concept_links 테이블 + 시드 전략(병목 상위 30~50 + 결측 허용 계약), 결과 카드 links 부착(preview 포함 — 무료 존), 학습 큐 응답 계약(reason 사람 언어 문구 + goal primary), 공유 노드 귀속 타이브레이크, R4 링크 점검 운영, 결정 U1~U6.

(b) 왜 이렇게 나눴나: 큐 생성·위상정렬 자체는 spec-01 소관 — 본 spec은 그 출력을 채우고 보여주는 층. additive 컬럼 2건(source_concept_id·goal_concept_id)과 provenance 운반 책임만 제안, 확정 결정 재오픈 아님.

(c) 맞물림: 링크 테이블·시드는 백엔드(spec-01 구현)와, 경로 강조는 프론트(spec-02 hook의 highlightPath 옵션)와 각각 병렬 가능. ⑥ 경로 강조는 신규 백엔드 없이 프론트 조립.

3. 사인오프된 결정 표

F-1~F-4 — 제품/UX knob (PRD §0.1, 전부 확정) ✅ 사인오프

코드무엇을 정했나채택안기각안·이유
F-1로그인 게이트 위치 + CTA 위계결과-시점 reverse gate. 진단은 비로그인 완주. 무료 = 진단 결과 그 자체(헤드라인 + 카드 시급도순 + 개념별 무료 외부링크), 게이트 = 독점 자산(인터랙티브 그래프 학습 경로 + 저장·재열람). 화면 단일 1차 CTA = "저장하고 학습 경로 시작하기"(로그인 트리거), 카드별 "경로 보기"는 2차 강등. 원칙: 이미 공짜인 공공자료(EBS)는 게이트하지 않음선행 로그인 게이트 — "가치 먼저, 계정 나중" 원칙 위배. N개 CTA 경쟁도 함께 제거
F-2익명 진척 복구문답 중 localStorage answered-map 저장 → 이탈 후 재개, 결과-시점 로그인에서 계정 귀속. 서버 주도 stateless 순회와 정합 — 이 결정이 spec-01 D1-A(stateless)의 전제를 확정(스펙에 명시적 기각안 미기재 — 서버 세션 저장 방식은 spec-01 §4.3에서 기각)
F-3영역 진입 방식스마트 default + ±후보 pick-list. 학년 기반 시기 추정 단원을 소프트 default로(hard auto-start 아님), 선후순 ±후보 원탭 + escape 두 갈래 필수: (a) 다른 단원 직접 선택 (b) "모르겠어 → 전체 훑기". 고른 단원 = 시작 프론티어(경계 아님) — drill-down은 단원 밖 선수로 자유롭게 내려감. 카피 "지금 어디쯤이야?"escape (a)만 — "그냥 약점 궁금한" 유저가 억지로 단원을 고르게 됨 → (b)가 필수. 별도 모드 선택 UI는 MVP 비범위
F-4결과 출구 · 홈 입구 · top-N출구 = 통합 학습 큐(A안): 공유 선수지식을 병합한 하나의 계단 — 위상순(선수 먼저)이 지배 정렬, DKT 시급도는 진입 우선순위로만. 재진입: 큐 순서+완료여부+현재 위치 저장, 완료 = 유저 self-mark, 재진단은 별개 액션. 홈: 1차 "무료 진단 시작" 단독 압도, 그래프는 히어로 비주얼(미끼). top-N: '상' 등급만 default, 바닥 3(부족 시 '중' 보충)·캡 5, 나머지 "더 보기"개별 경로 N개 — 단일 계단 아님. 순수 시급도순 정렬 — "3단 건너뛰고 5단부터"로 계단 파괴. C안 경로 맵 미리보기·홈 B안 저커밋 진입로 = fast-follow 백로그

PRD에는 이보다 앞서 3대 트레이드오프 P-1(주 타깃 = 중·고등 셀프러너 학생) · P-2(추천 단위 = 개념 카드 top-N) · P-3(결과 1차 CTA = 그래프 학습 경로, 외부링크 보조)도 사인오프됨 (PRD §0).

S1~S6 — spec-01 백엔드 (S2·S3 = 리뷰 확정, 나머지 = 잠정 채택)

코드상태무엇을 정했나채택안기각안·이유
S1▶ 잠정익명 결과 산출A — 무영속 preview + 로그인 시 재제출 귀속. users_tests.user_id FK 무변경, F-2 localStorage와 정합, 서버에 익명 잔재 없음. 착수 시 재검토 꼬리표B 게스트 행 영속화 — user_id nullable 마이그레이션 + 고아 행 정리 배치 필요
S2✅ 확정self-report 답안 저장 스키마C — 신규 self_report_answers 테이블 + probabilities.user_test_id additive. 신규 경로는 구 answers를 읽지도 쓰지도 않음 → R1(공유 테이블 오염) 소멸. 세션 단위는 기존 users_tests 재사용. 임시답/가짜 item 매핑 금지(오염을 '조용한 오염'으로 은폐)구 A안 — answers.item_id NOT NULL 완화. 리뷰 R1 확정으로 기각: 롤백용으로 살아있는 findBefore가 NULL item_id 행을 전체 이력으로 긁어 items→concepts 조인이 깨짐
S3✅ 확정DKT 입력 구성A — 현재 세션 answered-map만 ×10 증폭. 근거 = preview와 귀속 결과의 결정론 동치(F-1 "본 결과를 저장") 보장 + 스냅샷 설명가능. R2(빈/얇은/단조 입력) 가드 전제: 몰라요 0개 → DKT 호출 생략·정상 결과, 대표 4 시나리오 실측, fail-softB 과거 self-report 세션 병합 — preview·귀속 결과 불일치로 F-1 위반
S4▶ 잠정등급 컷 출발값HIGH: p<40 · MID: 40≤p<65 · LOW: p≥65 — 구 ResultView 40/65 임계 선례 승계. 출발값일 뿐 — self-report 매핑 입력의 percent 분포는 실채점과 다를 수 있어 승계가 출발값 이상을 의미하지 않음. R2 실측 분포와 함께 보정(백로그)(대안 미기재 — 실데이터 부재로 임의 컷 신설 대신 선례 승계)

4. 교차 불변식 — 한 파일만 봐선 안 보이는 계약

① 결정론 시퀀스 순서 — preview == 귀속 결과 (순서 포함)

DKT는 RNN 계열이라 입력 순서에 민감하다. 따라서 "preview에서 본 결과를 저장한다"(F-1)가 성립하려면 두 시퀀스가 순서까지 일치해야 한다: preview는 요청 answered[] 배열 순서 그대로, 귀속 재조회는 self_report_answer_id ASC(= 저장 입력 순서) — 두 순서의 일치가 결정론의 필요조건 (spec-01 §4.4-2). 프론트 측 필요조건이 spec-02에 미러링된다: localStorage의 answered[]는 답변 순서 보존 계약(append-only) — 재정렬·dedup·재직렬화로 순서를 흐트리지 않고 재제출 페이로드도 그 순서 그대로 (spec-02 §4.2). ×10 증폭은 순서 확정 후 반복하며, 저장은 개념당 1행(UNIQUE(user_test_id, concept_id)). 검증 = 순서 포함 동일 property 테스트 (spec-01 §8, spec-02 §6).

② 롤백 — 신·구 병행 + 이미지 전환 (재빌드·git revert 아님)

백엔드: 롤백 = mmt.diagnosis.enabled=false. S2=C로 신규 테이블·컬럼이 전부 additive이고 구 경로(answers·/weakness-diagnosis·findAIInput/findBefore)는 무변경 + 신규 경로가 일절 접촉하지 않으므로 "구 경로 무변경 = 롤백 대상"이 실제로 성립한다 (spec-01 §4.7). 프론트: 구 Vue와 신 React는 별도 이미지(태그)로 공존 — 롤백 = 이미지 전환. 이것이 T5(web-react/ 병행)의 채택 이유이자, web/을 런치까지 무변경 보존해야 하는 이유다 (spec-02 §2.1·§7 T5). 즉 spec-01의 플래그 롤백과 spec-02의 이미지 롤백이 한 쌍이다. 신규 경로의 구 테이블 무접촉은 property 테스트로 증명한다(R1 소멸 증명, spec-01 §8).

③ 계약 SSOT — spec-01 shape가 정본, 드리프트는 스냅샷으로 감지

spec-01 §4.1/§4.3/§4.4의 요청·응답 shape가 정본이고, 프론트는 이를 TS 계약 타입 모듈(예: src/api/contracts.ts)로 옮겨 mock과 실클라이언트가 같은 타입을 참조한다 — 병렬 개발(mock 선개발)의 드리프트 방지 장치 (spec-02 §5). spec-03의 links shape·highlightPath 옵션도 같은 SSOT에 등재된다 (spec-03 §3.1·§3.3). 한계 명시: 이 SSOT는 드리프트의 사후 감지(게이트 결정론 스냅샷)까지 — Java DTO↔TS 타입의 컴파일 타임 예방은 codegen이 필요하며 T1 범위 밖 → 백로그.

④ 큐 provenance — reason·goal 귀속 타이브레이크 = §4.6 진입 우선순위 미러

공유 선수 병합이 통합 학습 큐(spec-01 §4.6)의 존재 이유인데, 바로 그 병합 노드에서 한 개념이 여러 카드의 폐쇄에 동시 소속될 수 있다. reason(U3)과 goal(U6)의 귀속이 자의적이면 UX 약속이 깨지므로, 귀속 타이브레이크 = 큐 진입 우선순위 규칙의 미러: 소속 카드 중 최고 시급도(최저 percent) → 동률 시 conceptId 오름차순 — 결정론까지 승계한다 (spec-03 §3.2). 캐비어트 2건: (1) 스키마는 additive지만 큐 생성 알고리즘이 위상 병합을 관통해 출처를 계산·운반하는 새 책임을 획득 — "컬럼 하나 추가"보다 무거움. (2) goal의 "항상 정의" 불변식은 provenance 완전성에 종속 — 병합 경로 어디에서도 NULL로 새지 않는지가 실질 관문(property 테스트가 가드). source/goal_concept_id는 스키마 nullable + 애플리케이션 non-null 강제가 의도된 설계 (spec-03 §6 구현 감시 2건).

⑤ fail-soft·결측 허용 — 부분 실패가 학생을 막다른 골목에 두지 않음

TF Serving 실패 시에도 문답·"몰라요" 목록까지는 성립(시급도 등급만 결측) (spec-01 §4.7) — 프론트는 게이트 재제출 실패 시 이 fail-soft 결과를 렌더한다(에러가 아니라 결과 degrade) (spec-02 §4.4·§4.6). 같은 원칙이 링크에도: 링크 0개 개념은 섹션 자체 생략(결측 허용 계약), EBS 대규모 개편 시 provider 단위 일괄 비노출로 서비스는 링크 없이도 성립 (spec-03 §2.2·§4). "몰라요" 0개(전부 알아요)도 에러가 아니라 DKT 생략 + "약점 없음" 정상 결과 (spec-01 R2).

6. 용어·약어 키 + 핵심 인용

DKT (Deep Knowledge Tracing)
기존 TF Serving 모델. [skillId, answerCode] 시퀀스를 받아 개념별 이해 확률 probabilityList를 반환(probabilityList[skillId-1] 1-based 인덱싱). M7에서 입력만 self-report 매핑으로 교체, 모델 자체는 무변경.
self-report OX
학생이 개념을 "알아요/몰라요"로 자가응답. 정오답 매핑 = 안다=맞음(1) / 모른다=틀림(0). 변환은 저장 시가 아니라 DKT 시퀀스 생성 시 조회 변환(known BOOLEAN 그대로 저장).
answered-map
[{conceptId, known}] 배열. 익명 문답의 전체 상태이자 매 요청에 실려가는 stateless 순회의 입력. 프론트는 localStorage mmt.diagnosis.v1에 append-only로 보존.
시작 프론티어 (frontier)
선택 단원 개념들 중 단원 내 후수-최상위(같은 단원의 다른 개념이 자기를 선수로 요구하지 않는 개념). 문답의 시작점이지 경계가 아님 — drill-down은 단원 밖으로 내려갈 수 있다.
inferred-known
"알아요" 응답 시 그 개념의 선수 폐쇄 전체(findPrerequisitesWithDepth(C, 10))를 아는 것으로 마킹해 이후 질문에서 제외 — 화면 수 급감의 핵심.
blockedDescendants (S6)
"이걸 모르면 위로 N개가 막혀요"의 N. 역방향 재귀 CTE(to_concept_id=P → from_concept_id, 기존 선수 CTE의 미러)로 depth 3 transitive distinct count. 카드의 사람 언어 근거(urgencyBasis)이자 U2 시드 선별 기준.
knowledge_space 방향성 (M2 승계)
from_concept_id = 후수(뒤에 배움) / to_concept_id = 선수(먼저 알아야 함). 개념 C의 선수 = WHERE from=C, 개념 P를 막는 후수 = WHERE to=P(역방향).
self_report_answers (S2=C)
self-report 답안 전용 신규 테이블. 구 answers(item FK 필수)와 완전 분리 — 신규 경로는 구 테이블을 읽지도 쓰지도 않음(R1 소멸).
통합 학습 큐 (F-4)
top-N 취약 개념들의 공유 선수지식을 병합한 단일 계단. 위상순(선수 먼저)이 지배 정렬, 시급도는 Kahn 진입차수 0 후보가 복수일 때의 진입 우선순위로만. 사이클 발견 시 간선 drop + 경고(생성이 죽지 않게 degrade).
provenance (U3·U6)
큐 항목이 어느 취약 카드의 폐쇄에서 왔는지의 출처. source_concept_id(reason 문구 소스)·goal_concept_id(primary 목표)로 큐 생성 시 계산·저장. 귀속 타이브레이크 = 최고 시급도 → conceptId ASC.
결과-시점 reverse gate (F-1)
로그인을 진단 앞이 아니라 결과 시점에 요구. 무료 = 결과 자체(preview), 게이트 = 저장·큐·인터랙티브 경로. 게이트 통과 시 localStorage answered-map 재제출로 계정 귀속.
결측 허용 계약 (U2)
링크 0개 개념은 카드·큐 항목에서 링크 섹션 자체를 생략 — "준비 중" 문구 없음. 전 개념 시드가 런치 전제 조건이 되지 않게 하는 장치.
fail-soft
TF Serving 실패 시 시급도 등급만 결측되고 "몰라요" 목록 기반 결과는 성립 — 런치 차단 요소 아님. 프론트는 에러가 아니라 결과 degrade로 렌더.
mmt.diagnosis.enabled
신규 경로 전체(/diagnosis/*·/learning-queues/*)의 피처 플래그(기본 false). 백엔드 롤백 스위치. 신규 영역 mmt.diagnosis.*는 ADR 기록 후 등록.
계약 SSOT
spec-01의 요청·응답 shape가 정본 → 프론트 TS 타입 모듈(contracts.ts)로 단일 참조. 드리프트는 스냅샷 테스트로 사후 감지(codegen 예방은 백로그).

CREATE TABLE self_report_answers (
  self_report_answer_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_test_id          BIGINT  NOT NULL,   -- FK users_tests (기존 세션 재사용 — 별도 세션 테이블 신설 안 함)

7. 이 자료로 답할 수 있는 복습 질문

  1. D3(시급도 = 그래프 점수)이 D3-R(DKT 유지)로 역전된 이유는 무엇이고, 그 대가로 감수한 리스크(R1)와 방어책은 무엇인가?
  2. S2에서 구 A안(answers.item_id NOT NULL 완화)이 기각된 구체적 메커니즘은? — findBefore와 items→concepts 조인 관점에서 설명하라.
  3. "preview == 귀속 결과"의 결정론이 깨질 수 있는 지점 두 가지(백엔드 재조회 순서 / 프론트 localStorage)와 각각의 방어 계약은 무엇인가? DKT가 RNN이라는 사실이 왜 여기에 관여하는가?
  4. 통합 학습 큐에서 "순수 시급도순 정렬 금지"인 이유는? 시급도는 정렬에서 정확히 어떤 역할로 제한되는가?
  5. 공유 선수 노드의 reason·goal 귀속 타이브레이크 규칙은 무엇이고, 왜 spec-01 §4.6 진입 우선순위를 미러해야 하는가?
  6. M7 전체 롤백 시나리오를 백엔드·프론트로 나눠 설명하라 — 왜 git revert나 재빌드가 아닌가? 이것이 T5(web-react/ 병행) 채택과 어떻게 연결되는가?
  7. "몰라요" 0개(전부 알아요) 세션과 TF Serving 장애는 각각 어떻게 처리되는가? 두 경우 모두 에러가 아닌 이유는?
  8. U6 goal이 "유일 목표"가 아니라 "primary"로 표기되는 이유는? (힌트: escape(b) 전체 훑기 → 다중 프론티어 → 큐의 그래프 형상)
